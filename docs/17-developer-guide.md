# 17 — Developer Guide (Local Development)

This document is for whoever is actively building/modifying this codebase — human or AI agent — as opposed to `16-installation.md`, which is for the school staff running it in production.

## Local dev setup (without full Docker stack)

For fast iteration, you don't need to run everything in Docker during development:

```bash
# Backend
cd backend
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env   # point DATABASE_URL at a local sqlite file
alembic upgrade head
uvicorn app.main:app --reload --port 8000

# Frontend
cd frontend
npm install
npm run dev   # Vite dev server, proxies /api to localhost:8000 (configure in vite.config.ts)
```

Run **Ollama and ChromaDB via Docker** even in local dev (they're awkward to install bare-metal consistently across OSes), using the `docker-compose.override.yml` mentioned in `14-docker-deployment.md`:

```bash
docker compose -f docker-compose.yml -f docker-compose.override.yml up ollama chromadb
```

This gives a fast backend/frontend reload loop while still using real AI services locally.

## Database migrations workflow

- Never hand-edit the SQLite file directly during development.
- Any schema change → create an Alembic migration:
```bash
alembic revision --autogenerate -m "add duplicate_score to question_bank"
```
- **Always review autogenerated migrations before applying them** — Alembic's autogenerate is good but not perfect, especially around SQLite's limited `ALTER TABLE` support (SQLite often needs a "create new table, copy data, drop old, rename" pattern for changes autogenerate may not produce cleanly — verify manually).
- Apply with `alembic upgrade head`; never apply migrations directly to the production volume without a backup first (per `14-docker-deployment.md`).

## Code style and conventions

- **Backend**: `black` + `ruff` for formatting/linting, type hints everywhere (this is a Pydantic/FastAPI codebase — type hints aren't optional decoration, they're load-bearing for validation). Run `mypy` in CI if feasible.
- **Frontend**: `eslint` + `prettier`, strict TypeScript (`strict: true` in `tsconfig.json`) — don't loosen this to silence errors; fix the underlying typing instead.
- Follow the router-thin/service-thick split from `04-backend-specification.md` consistently — if you find yourself writing a multi-step DB transaction directly inside a router function, move it to `services/`.

## Working with the AI Pipeline during development

- Mock Ollama responses for fast iteration on agent logic (per `15-testing.md`) — don't wait on real LLM calls for every dev loop iteration when you're working on, say, the JSON-parsing/DB-writing logic of an agent rather than the prompt itself.
- When you do need to test against real Ollama output, keep a small, fixed set of "known good" test PDFs (one per subject/grade band) in a `fixtures/` folder so prompt iteration has a consistent baseline to compare against, rather than testing against whatever random book happens to be loaded.
- Log every prompt sent and raw response received during local development (a `LOG_LLM_CALLS=true` env flag) — this is the fastest way to debug why a generated question came out wrong.

## Adding a new module end-to-end (checklist)

When adding a new feature area, touch things in this order to avoid backtracking:

1. `03-database-schema.md` — does this need new tables/columns? Update the doc, then write the Alembic migration.
2. `04-backend-specification.md` — add the service function(s) and router.
3. `13-api-reference.md` — document the new endpoint(s).
4. `12-security.md` — confirm role/scoping rules for the new endpoints, add audit log calls.
5. `05-frontend-specification.md` — add the module/route, API client functions, hooks, components.
6. `15-testing.md` — add the required test scenarios for this module to the relevant table.
7. Update `00-README-START-HERE.md`'s build-order table if this is a new top-level module.

## Branching/release conventions

- `main` is always deployable.
- Feature work on short-lived branches, merged via PR.
- Tag releases (`v1.0.0`, etc.); `14-docker-deployment.md`'s "Updating the application" instructions assume a tagged release bundle, not an arbitrary commit.

## Useful local commands reference

```bash
# Run backend tests
pytest backend/tests -v

# Run frontend component tests
cd frontend && npm run test

# Run E2E tests (requires backend+frontend running)
cd frontend && npx playwright test

# Seed competency taxonomy (required before first AI pipeline run, per 07-rag-architecture.md)
python backend/scripts/seed_competencies.py

# Manually trigger a single pipeline stage for debugging
python backend/scripts/run_pipeline_stage.py --book-id 1 --stage concept_extraction
```

(Exact script names/flags are an implementation detail — keep this section updated to match what actually exists in `scripts/` as the codebase grows.)
